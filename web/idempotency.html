The four designs

The rules that make it work

  1. Claim the key atomically, before the side effect. INSERT ... ON CONFLICT DO NOTHING on a unique key. A read then write is a race, however fast it looks.
  2. Store the response, replay it. A retry should get the original receipt (same charge id), not a 409, or the client can't tell whether it paid.
  3. Fingerprint the request. Same key with a different body is a client bug: answer 422 instead of silently replaying the wrong result.
  4. Release the key when nothing happened. If the provider definitely didn't charge, delete the claim so a retry can succeed. Otherwise the customer is locked out.
  5. Answer 409 while in flight. Concurrent duplicates shouldn't wait on, or race, the first attempt.

The hard case this lab leaves out: the provider times out and you don't know if it charged. Then you can't release the key; you reconcile with the provider first. More on that in this write-up.
